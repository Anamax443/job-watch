Mind map

Not the architecture, but the decisions and the reasons behind them. Almost every branch of this map came out of a specific incident, not out of greenfield design. If you want to know how the agent works, go to the information flow; this is about why it is built the way it is.

Five questions the project rests on

Where these decisions came from

Code decides the region On 5 Aug 2026 the agent sent a Prague ad with a score of 80/100 and the reasoning that the location was in Prague, which is in the preferred region, even though the settings said Brno. The rule was only a sentence in the prompt and the weak model ignored it. Hard criteria do not belong in a prompt.
A queue instead of dropping A daily run actually scored 3 out of 91 candidates and dropped 88 — the increment is fetched only once and the cursor had moved on. Since then, whatever is not scored is stored without a score.
Failure returns null Number(null) is 0, and zero in the loop means done — the ad would have been stuck forever. A test found it while being written, not production.
Measure inside the deployed version The eval set first called Claude directly, but production scored via the free model. It was measuring a different rung of the ladder than the one that decides. An instrument pointed at the wrong thing is worse than none — it manufactures false confidence.
Third-party text as data Anyone can write an ad description. Until 1 Sep 2026 it was pasted straight into the query; the damage was bounded only by the JSON schema and the region cap — luck of the design, not a defence.
A question mark instead of a silent drop An ad without a location could never pass — the cap held it below the threshold. Yet a lead should not be lost because of an empty field. The region could not be derived elsewhere (4 of 5 such ads do not name a town even in the description), so it passes with a ⚠ instead.
